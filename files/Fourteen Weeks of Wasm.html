1. How to use this plan

  • Weekly budget (~10 h): ~3.5 h reading, ~5 h lab, ~1.5 h notes, flashcards, and the proposal tracker.
  • Reading tiers: Core is required. Depth is optional and marked. Historical means the piece is old but still the best explanation of a design decision; read it for the reasoning, not the version numbers.
  • Labs are self-checked builds. Each has an explicit exit check. Do not move on until the exit check passes; the labs stack.
  • Timeline tags on each week say when the material entered the standard: MVP (1.0), 2.0, 3.0, P1–P5 (proposal phase as of 2026-09-04), WASI 0.2, WASI 0.3, CM (Component Model).
  • Proposal tracker (§7): update it every two weeks. It is the "roadmap" half of this course, and it goes stale fast.
  • Capstone: choose from the menu in §6 during Week 9. Weeks 10–14 reserve ~5 h/week for it.
  • Lab languages: Rust produces most modules and components; Python is the host and driver wherever the tooling allows; C appears twice so the classic LLVM/Emscripten/wasi-sdk path is not a mystery. Rationale in §4.

2. The spine — Wasm as a designed artifact under four constraints

SafeRuns untrusted code. Linear memory is sandboxed by construction; control flow is structured; validation precedes execution.
FastNear-native and predictable. Single-pass compilation, streaming, cheap bounds checks, and tiers because startup and peak speed pull apart.
PortableNo undefined behavior. A deterministic profile since 3.0. Relaxed SIMD trades this away on purpose, which is why it is separate.
ComposableHost-agnostic. Imports and exports are the only doors. WASI and the Component Model make them typed and language-neutral.

Recurring question for every week: what did this feature cost on the other three constraints?

Every feature in this course is taught as a trade-off among these four. When a proposal looks arbitrary, ask which constraint it serves and which one it strains.

4. Week 0 — Toolchain (optional, ~6 h; ~12 h if you also need Rust basics)

Why Rust and not Python everywhere. Python cannot produce a core Wasm module from ordinary Python code. It can host Wasm (wasmtime-py) and it can be packaged as a component (componentize-py bundles a CPython build). Rust is the reference toolchain for the Component Model: wasm32-wasip2 is a Tier 2 target, wit-bindgen and wasm-tools are Rust-first, and most primary documentation assumes it. The labs need only basic Rust: functions, structs, Option/Result, cargo, crates. Budget 6–8 h of "Rust by Example" if you have never written Rust.

5. Week-by-week

Part I — Foundations (Weeks 1–4)

Lens: language and semantics, with the sandbox as the first systems idea.

Week 1

What Wasm is and why it exists

MVP3.0
  • Goal: explain, in your own words, what a .wasm file is, what a module and an instance are, and where Wasm runs. Run the same module in three hosts.
  • Concepts: the four constraints (§2); asm.js → Wasm; the stack machine; modules, instances, imports, exports; linear memory; the host boundary; browser vs Wasmtime vs edge; what Wasm is not (not a language, not a VM in the JVM sense, not fast by magic).
  • Core reading:
    • Andy Wingo, "WebAssembly: Yes, but for What?", ACM Queue 23(3), 2025. Where Wasm actually wins today. Read first; it sets expectations.
    • MDN, "WebAssembly concepts" and "Understanding WebAssembly text format". Maintained (last updated Jul 2026).
    • webassembly.org, "Wasm 3.0 Completed" (Sep 17, 2025). The current feature set in one page.
    • Web Almanac 2025, WebAssembly chapter (Jan 2026). Wasm is on 0.35% of desktop sites; .NET/Blazor is the top source (41.7%), Emscripten second (10.1%). Read for calibration.
  • Historical: Lin Clark, "A cartoon intro to WebAssembly" (Mozilla Hacks, 2017, 6 parts). The best explanation of the stack machine and why compilation is fast. Ignore the 2017 status claims.
  • Lab 1 — One module, three hosts (~5 h):
    1. Write add(i32, i32) -> i32 and fact(i32) -> i32 by hand in WAT. Assemble with wat2wasm. Disassemble with wasm-objdump -x and wasm-tools print.
    2. Run both in Wasmtime CLI (wasmtime run --invoke), from Python (wasmtime package), and in a browser page (WebAssembly.instantiateStreaming).
    3. Compile the same two functions from Rust (wasm32-unknown-unknown) and from C (wasi-sdk). Compare binary sizes and the exported names.
    • Exit check: you can read the WAT for fact and point to the loop, the branch, and the locals without looking anything up.
  • Self-check: What is the difference between a module and an instance? Why does structured control flow matter for the safe constraint? Name two things Wasm cannot do without a host import.
Week 2

Binary format, text format, and structured control flow

MVP
  • Goal: parse a real .wasm binary with your own code and explain every section.
  • Concepts: sections (type, import, function, table, memory, global, export, start, element, code, data, custom); LEB128; value types; function bodies; block/loop/if; br/br_if/br_table as labeled exits, not gotos; call/call_indirect and tables; loads/stores with alignment hints; traps; the name custom section.
  • Core reading:
    • Dubroy & Guerra, WebAssembly from the Ground Up (wasmgroundup.com; $19 as of Sep 2026). Chapters 1–8. You build a compiler that emits Wasm, which is the fastest way to learn the binary format.
    • Haas et al., "Bringing the Web up to Speed with WebAssembly", PLDI 2017, §1–2 only. The design rationale for structured control flow and the stack machine.
    • Spec, "Structure" and "Binary Format" chapters. Skim; use as reference while parsing.
  • Depth: Dan Gohman's WebAssembly Reference Manual (MVP-era, stale but readable).
  • Lab 2 — A binary parser in Python (~5 h):
    1. Write a parser that reads a .wasm file, decodes LEB128, walks the sections, and prints types, imports, exports, and each function's instruction list with nesting depth.
    2. Test it on your Week 1 binaries and on a clang-produced C binary. Cross-check against wasm-tools print.
    3. Add a --dot flag that draws the control-flow nesting of one function (blocks as boxes, branches as labeled edges).
    • Exit check: the parser handles every MVP section in a wasi-sdk hello-world without error, and your export list matches wasm-objdump -x.
  • Self-check: Why can br only target enclosing labels? What does call_indirect check at run time, and which constraint does that serve? What is the alignment immediate on a load actually used for?
Week 3

Validation as a type system; execution semantics

MVP3.0
  • Goal: turn the parser into a validator and an interpreter for a core subset, and pass official spec tests for that subset.
  • Concepts: operand-stack typing; validation rules per instruction; unreachable and stack polymorphism; small-step reduction; the store, frames, and labels; traps as termination; determinism and the 3.0 deterministic profile; why the spec has both a formal semantics and a reference interpreter; SpecTec (one DSL source generates the prose, the LaTeX, the Coq definitions, and the AST).
  • Core reading:
    • Haas et al., PLDI 2017, §3–4 (validation and execution), read alongside the spec's "Validation" and "Execution" chapters for the same instructions. Take the rules for i32.add, block, br_if, and call and work them by hand.
    • webassembly.org, "SpecTec has been adopted" (Mar 27, 2025), and Youn et al., "Bringing the WebAssembly Standard up to Speed with SpecTec", PLDI 2024, §1–2.
  • Depth: Conrad Watt, "Mechanising and Verifying the WebAssembly Specification", CPP 2018 (§1–3: what mechanization found). Watt et al., "Two Mechanisations of WebAssembly 1.0", FM 2021 (skim).
  • Lab 3 — Validator + interpreter for a core subset (~6 h):
    1. Subset: i32/i64 arithmetic and comparisons, local.*, global.*, block/loop/if/br*, call, return, memory.size/grow, i32.load/store.
    2. Implement validation (type-stack per control frame) before execution. Reject bad modules with the spec's error names.
    3. Convert spec tests with wasm-tools json-from-wast and run i32.wast, block.wast, loop.wast, br_if.wast, call.wast, memory_grow.wast against your interpreter.
    • Exit check: all assertions pass for those six files. Keep this code; it is the seed of Capstone B.
  • Self-check: What does the validator know that the interpreter can then skip checking? Why is unreachable typed the way it is? What does SpecTec change about how a proposal's spec text is written?
Week 4

Memory, safety, and the sandbox

MVP3.0P3
  • Goal: state precisely what Wasm sandboxing guarantees and what it does not, and measure one cost of it.
  • Concepts: linear memory and bounds checks; guard pages vs explicit checks; 32-bit vs 64-bit address space (memory64, 3.0; Safari not yet shipping); multiple memories (3.0); custom page sizes (Phase 3); control-flow integrity through typed call_indirect; the binary security gap (no ASLR, no stack canaries, no page permissions inside linear memory); Spectre and SFI; verified SFI (VeriWasm); RLBox in Firefox as sandboxing in production; performance vs native.
  • Core reading:
    • Lehmann, Kinder, Pradel, "Everything Old is New Again: Binary Security of WebAssembly", USENIX Security 2020. The essential corrective to "Wasm is memory safe".
    • Jangda, Powers, Berger, Guha, "Not So Fast: Analyzing the Performance of WebAssembly vs. Native Code", USENIX ATC 2019. Read §1, §4–5, then the 2021 IMC follow-up abstract (Yan et al.).
    • Narayan et al., "Retrofitting Fine Grain Isolation in the Firefox Renderer", USENIX Security 2020, §1–3 (RLBox).
  • Depth: Johnson et al., "Доверяй, но проверяй: SFI safety for native-compiled Wasm" (VeriWasm), NDSS 2021. Narayan et al., "Swivel", USENIX Security 2021 (Spectre). Narayan et al., "Segue & ColorGuard", ASPLOS 2025 (near-zero-cost SFI on modern CPUs). Michael et al., "MSWasm", POPL 2023 (memory safety inside linear memory via handles).
  • Lab 4 — Break things inside the box (~5 h):
    1. Write a C program with a stack buffer overflow and a use-after-free. Compile with wasi-sdk. Show what corrupts (other data in linear memory) and what does not (the host, the call stack's return addresses, the engine).
    2. Compile the same program with -m64-style memory64 (Emscripten -m64 or Rust wasm64-unknown-unknown, Tier 3). Note the size and the toolchain friction.
    3. In Wasmtime, run a load-heavy kernel with guard pages enabled vs disabled (-O memory-guard-size=0 vs the default; older releases used static-memory-guard-size) and record the difference. Explicit bounds checks replace the guard pages when the guard is zero.
    • Exit check: a one-page note: three properties the sandbox guarantees, three it does not, and one measured number.
  • Self-check: Why can a Wasm program have an exploitable buffer overflow yet never escape the sandbox? What does memory64 cost on the fast constraint? Why does the deterministic profile exclude relaxed SIMD?

Part I exit criteria: your parser + validator + interpreter pass the six spec files; you can explain module/instance/store/frame; you can write the sandbox guarantee and its limits from memory.

Part II — Engines and systems (Weeks 5–8)

Lens: engines. How the four constraints are paid for at run time.

Week 5

Engines and compilation tiers

MVP
  • Goal: explain why every serious engine has more than one execution tier, and measure the trade-off yourself.
  • Concepts: interpreter vs baseline (single-pass) vs optimizing compiler; startup vs peak; streaming and lazy compilation; dynamic tiering; code caching; AOT vs JIT outside the browser; pre-initialization (Wizer) and partial evaluation (weval).
    • V8: DrumBrake (interpreter), Liftoff (baseline), Turboshaft (optimizing; replaced TurboFan for Wasm in 2025).
    • SpiderMonkey: Rabaldr (baseline), Baldr/Ion (optimizing).
    • JavaScriptCore: IPInt (in-place interpreter; Safari 26.0 runs Wasm here first), BBQ (baseline JIT), OMG (optimizing JIT).
    • Wasmtime: Cranelift (optimizing; ISLE instruction selection, regalloc2, ægraphs), Winch (baseline), Pulley (portable interpreter).
    • Wizard: simple interpreter, fast in-place interpreter, single-pass compiler — built for teaching and research.
    • WAMR: classic/fast interpreters, LLVM AOT, JIT. Wasmer: singlepass / Cranelift / LLVM backends.
  • Core reading:
    • Ben Titzer, "A Fast In-Place Interpreter for WebAssembly", OOPSLA 2022. Why Wasm is unusually hard to interpret fast, and the fix.
    • V8, "WebAssembly compilation pipeline" and docs/wasm/architecture.md; V8 blog, "Leaving the Sea of Nodes" (Mar 2025).
    • Wasmtime docs: "Cranelift overview", "Winch", and the "Wasm proposals" support matrix.
    • Chris Fallin's blog: "Cranelift, Part 3: Correctness in Register Allocation", the ægraphs post, and "regalloc2". No peer-reviewed design paper exists for regalloc2 or ISLE; the blog is the primary source.
  • Depth: Fallin & Bernstein, "Partial Evaluation, Whole-Program Compilation" (weval), PLDI 2025. VanHattum et al., "Lightweight, Modular Verification for WebAssembly-to-Native Instruction Selection" (Crocus), ASPLOS 2024. Zhang et al., "Research on WebAssembly Runtimes: A Survey", TOSEM 2025 (map of the field).
  • Lab 5 — One binary, five engines (~5 h):
    1. Pick three kernels from PolyBench/C-wasm (or Sightglass) plus your Week 4 load-heavy kernel.
    2. Measure compile time and run time in: Wasmtime (Cranelift), Wasmtime (Winch, -C compiler=winch), Wasmtime (Pulley), Wasmer (singlepass and Cranelift), WAMR (interpreter and AOT), and Chrome (Liftoff-only via --no-wasm-tier-up vs default).
    3. Profile one kernel with wasmtime --profile=guest and open it in the Firefox Profiler.
    • Exit check: a table with 4 kernels × ≥6 configurations, and a paragraph explaining one surprising row.
  • Self-check: Why does a baseline compiler exist if an optimizing one is available? What does streaming compilation require of the binary format? What is the cost of a JIT that the browser pays and Wasmtime does not?
Week 6

SIMD, numerics, and performance engineering

2.03.0P2P4
  • Goal: vectorize an image kernel, measure it, and explain what "relaxed" buys and costs.
  • Concepts: fixed-width 128-bit SIMD (2.0); relaxed SIMD (3.0) and its permitted nondeterminism (FMA, lane select, NaN handling); FP16 (Phase 2; failed Phase 2 in 2024, re-polled Aug 2026); wide arithmetic (Phase 4; i64.add128, i64.mul_wide_*); autovectorization vs intrinsics; wasm-opt levels; realistic benchmarking (Wasm-R3).
  • Core reading:
    • Spec, "Vector Instructions" (skim the shape, not every op). Relaxed SIMD proposal Overview.md (the nondeterminism table).
    • Baek et al., "Wasm-R3: Record-Reduce-Replay for Realistic and Standalone WebAssembly Benchmarks", OOPSLA 2024. Why microbenchmarks mislead.
    • Wide Arithmetic proposal Overview.md. A small, current example of a Phase 4 feature.
  • Depth: Yan et al., "Understanding the Performance of WebAssembly Applications", IMC 2021. Go 1.27 release notes (GOEXPERIMENT=simd, 128-bit Wasm SIMD).
  • Lab 6 — Sobel/convolution in SIMD (~5 h):
    1. Implement a 3×3 convolution over a grayscale image in Rust (core::arch::wasm32 intrinsics) or C (wasm_simd128.h). Scalar, SIMD, relaxed SIMD (+relaxed-simd).
    2. Run in Wasmtime and Chrome. Add wasm-opt -O3 and record the delta.
    3. Check outputs bit-for-bit across scalar/SIMD/relaxed and across engines. Note any difference and trace it to a relaxed op.
    • Exit check: ≥2× speedup SIMD vs scalar, a bit-exactness table, and a sentence on when you would refuse to use relaxed SIMD.
  • Self-check: Which constraint does relaxed SIMD trade away, and how does the deterministic profile respond? Why is FP16 controversial enough to fail a phase vote? What does wide arithmetic accelerate?
Week 7

Threads, atomics, and the memory model

P4P1P2CM
  • Goal: run a parallel kernel in the browser, and explain why threads outside the browser are still unsettled in 2026.
  • Concepts: shared linear memory and atomics (Threads proposal, Phase 4 since Oct 2023; shipped in browsers since 2019–2021); memory.atomic.wait/notify; Web Workers, SharedArrayBuffer, COOP/COEP and crossOriginIsolated; the Wasm memory model ("Weakening WebAssembly"); why instances, tables, GC objects, and JS glue make "just add threads" hard; wasi-threads (deprecated; removed in Wasmtime 47); Shared-Everything Threads (Phase 1: shared annotations on GC types, tables, globals, thread-local globals); Acquire-Release Atomics (Phase 2, split out in May 2026); Component Model cooperative threads (implemented at the CM level; shipping in a WASI 0.3.x follow-up).
  • Core reading:
    • Conrad Watt, "Concurrency in WebAssembly", ACM Queue 23(3), 2025. The current state and the open problems, by the person driving them.
    • Threads proposal Overview.md; Shared-Everything Threads Overview.md (§ motivation and design).
    • Watt, Rossberg, Pichon-Pharabod, "Weakening WebAssembly", OOPSLA 2019, §1–2 only.
  • Depth: the full "Weakening WebAssembly" formal model. CG meeting notes for May 19, 2026 (the acquire-release split) and Oct 28–29, 2025.
  • Lab 7 — Parallel Sobel (~5 h):
    1. Port the Week 6 kernel to a thread pool in the browser. Easiest path: C with Emscripten -pthread. Rust path: wasm-bindgen-rayon (requires nightly -Zbuild-std with +atomics,+bulk-memory; note the friction).
    2. Serve with COOP/COEP headers. Measure scaling at 1, 2, 4, 8 workers.
    3. Try the same module under Wasmtime with -W threads. Observe what is and is not available for spawning threads now that wasi-threads is gone. Write down the 2026 options (host-driven, CM cooperative threads, or wait for Shared-Everything).
    • Exit check: a scaling plot and a half-page "state of threads outside the browser, Sept 2026".
  • Self-check: Why does the browser require cross-origin isolation for shared memory? What is a shared GC struct and why does it need a new proposal? What is the difference between Component Model cooperative threads and core Wasm threads?
Week 8

3.0P3P1
  • Goal: read and hand-write GC and exception-handling code, and explain what changed for Kotlin, Dart, Java, and Scheme toolchains.
  • Concepts: WasmGC (struct and array types, recursive type groups, subtyping, i31ref, casts, the any/eq/func/extern hierarchies); typed function references; tail calls (return_call); exception handling (try_table, exnref; the legacy EH instructions now live in the Legacy Extensions spec); JS string builtins (wasm:js-string); Custom Descriptors & JS Interop (Phase 3, Jan 2026: JS prototypes for Wasm GC objects); Reference-Typed Strings (Phase 1; contested); how engine GCs integrate with the host GC.

  • Core reading:
    • GC proposal MVP.md (the type system section) and the Exception Handling proposal Exceptions.md.

Week 9

The JavaScript embedding: JS API, JSPI, ESM integration, debugging
